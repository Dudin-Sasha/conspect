# Базовые принципы именования end-point'ов

1) Использовать существительные во множественном числе
	`Правильно - /Users  /Products`
	`Не правильно - /getUser  /createProduct`
2) Использовать вложенность (иерархию) для связи ресурсов
	`/Users/[userId]/orders`
3) Использовать Kebab-case[^1] (вообще CamelCase…) для сложных названий
	`/items/[itemId]/upload`
4) Избегать лишних слов (не добавлять глаголы если это не требуется)
	`Правильно - /products`
	`Не правильно - /getProducts`

# Как выбрать HTTP метод

1) Создать => POST => создает новый ресурс
	`POST /products`
	`POST /users/<userId>/upload`
2) Получить => GET => Возвращает данные не изменяя ресурс
	`GET /users`
	`GET /users/<userId>/profile`
	`GET /users?id=7`
3)  Обновить(Изменить) => PUT/PATCH => Обновляет существующий ресурс, PUT - полная замена, PATCH - частичная
	`PUT /users/<userId>/avatar` - тут как бы загружается фото на замену старого
	`PATCH /users/<userId>/Settings` - здесь пользователь изменил всего пару настроек
4) Удалить => DELETE => удаляет ресурс, либо помечает его удалённым по id
	`DELETE /users?id=2`
	`DELETE /users/<userId>` - предпочтительно использовать этот (но разницы нет)	``
# Когда использовать query-параметры

query-параметры - это параметры после вопросительно знака в URL
1) Необходимо фильтровать, сортировать или искать по данным
```Примеры
GET /products?Filters=status:'ordered' - фильтры
GET /products?sortKey=1 - сотировка по ключу
GET /products?name=ASC - сортировка по имени
GET /products?order=<name:"ASC";price:"DESC"> - фильтры по json параметрам (но ограничен URL)
GET /products?q=Android - Сортировка по содержимому
```
2) Пагинация (Page и Limit) - разбивка всех данных по страницам (как в каталогах условного DNS) - `GET /products?page=1&limit=20`
3) Передача данных которые не являются частью id ресурса
# Когда использовать path-параметры
path-параметры - это часть URL в фигурных скобках, обычно туда помещается ID или UUID
`GET /users/<userId>/profile`
1) Когда нужно указать обязательный идентификатор(Id) ресурса
2) Обращения к конкретному экземпляру ресурса
3) Реализация иерархического URL запроса
	`GET /users/<userId>/orders?status=Completed`
	
# Когда используется Body
в методах post put patch
body - строковое представление json объекта
```
POST /users
Body:{
	name:x
	lastName:z
	age:y
}

PATCH /user/:id/settings
Body:{
	editedSetting:true
}
```

# Правила формирования ответа

1) При формировании ответа на сервере с начала проверяется на доступность запрашиваемые данные.
2) Проверка на существование сопутствующих сущностей
3) Формирование структуры ответа на основе существующих сущностей в БД 
4) Когда сущность пополняется данными в результате запроса в ответе должна быть информация только о созданной сущности
5) В случае если пользователю не нужны обновлённые данные из БД, поскольку он сам их изменил, то ответ может быть пустым(обычно со статус кодом 200/204)
6) При поисковых запросах структура ответа зависит от вложенности сущности по который идет поиск

`GET /users/:id/history => [{user_id; rooms:[{lastmessage}] }]`

`GET /search?m=5000рублей => [{rooms:[{users:[{message}] }] }]`

[^1]: когда слова пишутся строчными буквами и разделяются дефисом
